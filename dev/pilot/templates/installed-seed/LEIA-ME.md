# Maestro MCP — piloto experimental

1. Extraia o ZIP inicial em uma pasta local e preserve o kit. A origem de atualizações é uma pasta **SOURCE** separada e persistente do time, sincronizada pelo OneDrive/SharePoint; marque essa origem como **Sempre manter neste dispositivo**. As próximas versões chegam por essa pasta, sem baixar outro ZIP nem reinstalar o Maestro.
2. No Mac, abra **Maestro.command**. No Windows, abra **Maestro.cmd**. Não execute como administrador. Se o sistema bloquear um programa ou script, preserve o bloqueio e peça orientação ao time; não desative as proteções.
3. A pasta Developer é criada localmente se ainda não existir. Na primeira vez, informe o diretório **já usado pelo owner do Maestro**, o workspace em Developer e o cliente desejado: **Desktop somente** ou **Code e Desktop**. A escolha Desktop não pede executável, perfil nem login do Code. O workspace sugerido pode ser criado pela instalação normal, depois da sua revisão. Não precisa escrever JSON, gerar IDs nem copiar arquivos para o brain. Se nunca usou Maestro, selecione a própria pasta Developer como base; a revisão normal mostrará a criação explícita de um home novo. Uma instalação existente fora de Developer precisa de orientação; este piloto não move dados. O workspace deve ser uma pasta de projeto separada do brain e da pasta do piloto.
4. Se escolheu **Code e Desktop**, escolha o **perfil Code privado do piloto**, separado do seu perfil normal. Na criação de um perfil novo, confirme que somente nele a memória automática e a sincronização de skills e plugins da conta ficarão desativadas. As skills do próprio Maestro continuam disponíveis pelo plugin do Maestro. Perfis existentes são preservados; configurações incompatíveis mantêm a qualificação pendente. Se necessário, o próprio programa abre o login oficial desse perfil. Nenhuma senha ou credencial é copiada. Esse mesmo perfil é usado pelo teste e pelos atalhos de gerenciar/atualizar; seu brain, owner e workspace continuam sendo os selecionados.
5. Na primeira inscrição da origem, informe o caminho local da pasta **SOURCE** sincronizada do time, fora da pasta do ZIP extraído. Confira o source ID, a versão e os efeitos na revisão original antes de digitar `YES`. **TESTE-LOCAL** seleciona explicitamente só a amostra `source` deste kit para um ensaio; essa escolha não acompanha outra pasta OneDrive. Enter deixa a etapa pendente. A preparação preserva o brain, cria somente os componentes revisados e usa a origem inscrita nas próximas atualizações. Para **Code e Desktop**, mantenha a opção **complete**; se a qualificação nativa estiver bloqueada, reporte a pendência. **Desktop somente** prepara seu conector e sua biblioteca de métodos sem qualificação do Code; hooks do Code não fazem parte dessa escolha.
6. Use o menu para testar. Quando selecionado, o Code recebe o prompt automaticamente pelo executável registrado. No Desktop, a primeira instalação/ativação da extensão e a importação de skills seguem as telas normais do cliente; escolha **2 — Testar ou continuar**. O menu mostra **uma etapa de cada vez** e copia somente o pedido dessa etapa para sua conversa. Comece em **Conferir ou continuar**. Use **Próxima etapa** apenas depois de conferir o resultado; o menu não decide que algo terminou. No perfil, responda uma pergunta por vez no cliente até a confirmação final. Para voltar a uma etapa já feita, use **Etapa anterior**; os dados existentes são conferidos e preservados. Confirme a instalação pelo gerenciador. Quando a confirmação corresponde ao pacote e contrato atuais, o menu preserva sua conversa e não reabre o instalador, inclusive quando o mesmo MCPB é reutilizado após atualização. Se o pacote ou contrato mudar, a instalação volta a ficar pendente. A versão/caminho da biblioteca de skills aparece no menu; a importação no cliente continua não observada e deve ser feita se ela ainda não estiver disponível. Confirmação de instalação não comprova conexão ou funcionamento. Se aparecer outro Maestro, pare e reporte a ambiguidade.
7. Registre os resultados na opção **7** e devolva somente **RELATORIO.md**. Os JSONs e logs locais são privados. Para acompanhar uma versão nova da pasta, use **8 — Atualizar** e confira os efeitos. A atualização só aplica após sua confirmação. O programa atualiza a conferência e mostra o caminho do relatório mais recente, preservando os anteriores.

**Teste rápido do MCP:** no menu, escolha **10 — Testar MCP automaticamente**. A escolha autoriza um documento sintético e um teste no histórico, concluído quando passa. O programa confere o MCP instalado, converte e relê o documento e testa pausar/retomar um trabalho, sem prompts para copiar nem ferramentas de desenvolvimento. Ele mostra um novo **RELATORIO.md** e volta ao menu, inclusive se houver uma etapa incompleta. Os relatórios anteriores ficam preservados. Confira a pendência e o item indicado antes de tentar novamente; use **5** para revisar a preparação ou envie somente o Markdown ao time. Nenhum arquivo conflitante será substituído nem conversor instalado automaticamente.

Esse resultado testa o servidor MCP; o uso real no Code e no Desktop continua separado. Login normal, instalação da extensão e importação de skills no Desktop, hooks, agentes, memória e agendamento mantêm suas próprias pendências. Abrir o programa e a conferência inicial continuam somente de leitura. Esta opção exige um kit novo compatível; os pacotes anteriores continuam com o funcionamento original.

**Pode começar pelo Desktop mesmo tendo escolhido os dois clientes.** Na pergunta **Preparar ou retomar o Code agora?**, Enter prepara o pacote Desktop completo e mantém a seleção **Code e Desktop**. Nenhum login, modelo ou comando do Code é iniciado nessa escolha. O Code, seus hooks e sua qualificação continuam pendentes; isso aparece no relatório. A extensão e a biblioteca de métodos ainda precisam da instalação normal no Desktop, e preparação não comprova conexão ou funcionamento.

Para concluir o Code depois, use **5 — Preparar ou retomar clientes**, escolha `YES` para o Code e siga o login oficial e a qualificação genuína. O Desktop já preparado é preservado; concluir o Code não reabre a instalação da extensão se seus bytes e contrato forem os mesmos. Se um pacote completo já estava atual, escolher apenas a atualização Desktop preserva esse registro: o relatório mostra que o Code não foi observado **nesta tentativa**, sem apagar a qualificação anterior nem tratá-la como um teste novo. O programa oferece somente os testes válidos para o escopo atual.

Quando os dois clientes estiverem preparados e você escolher o roteiro combinado, faça o teste no Code até **Pausar o trabalho**. Com a pausa confirmada, pressione **Enter** no menu da etapa para voltar e escolha **2 — Continuar no Desktop**. Confira e retome por lá; depois use **6 — Conferir persistência no Code** para a leitura final. No **Desktop somente** ou enquanto o Code estiver pendente/fora do escopo desta tentativa, o roteiro começa no próprio Desktop e não comprova passagem entre clientes.

O kit é de engenharia, tem validade limitada e aceita somente as duas versões e a fonte assinada previstas na admissão. Não é uma distribuição corporativa assinada. A origem compartilhada contém os artefatos e metadados assinados como dados. O instalador verifica e prepara as cópias executáveis locais; não depende de executar programas nem preservar bits executáveis na pasta sincronizada. O brain, o estado privado e os programas ativos ficam em Developer. Abra sempre a entrada local, sem depender de executar um `.command` diretamente no OneDrive. A sincronização sozinha não ativa versões, executa tarefas ou reinstala clientes.

O diagnóstico automático verifica preparação, vínculo, pacotes atuais e leitura pelo MCP. **Ele não comprova carregamento real do Desktop/Code, identidade/skills na conversa, hooks/agentes nativos, onboarding completo, conversão de documento nem rotinas de memória.** Esses resultados dependem dos testes nos clientes e ficam separados no relatório. As respostas do menu são autodeclarações do participante.

Somente ao enviar **Conferir um documento**, quando o conversor atual estiver pronto, o menu prepara o documento público sintético **maestro-pilot.docx** no workspace. Essa etapa preserva um arquivo idêntico e para se já houver outro arquivo nesse nome; nada é sobrescrito. O prompt pede conversão pelo MCP atual e leitura do artefato retornado, conferindo o marcador e a tabela. Se o runtime estiver pendente, essa parte permanece pendente e o restante do ensaio pode continuar. Um runtime com identidade divergente bloqueia a jornada. **As opções de conexão/leitura e `--check-only` não preparam esse documento nem escrevem no workspace.**

Se uma permissão expirar, for cancelada ou ficar sem resposta, encerre aquele turno. No menu da etapa, escolha **Conferir após interrupção** e envie a conferência somente leitura. Ela mostra o que realmente ficou salvo. Preserve o resultado anterior; uma nova tentativa bem-sucedida não apaga a falha. A ausência de dados não comprova recusa nem autoriza repetição automática. O teste **Testar a recusa da memória** pede uma recusa explícita separada; a expiração não conta como recusa. As outras etapas precisam de sua própria escolha e revisão.

Se faltar login, permissão, prova nativa ou uma parte da sincronização, a etapa fica pendente e os arquivos são preservados. Faça o login pelo fluxo normal do cliente; para sincronização incompleta, mantenha a pasta offline e execute de novo. Para divergência de owner/brain, assinatura, hash ou versão, compartilhe o relatório e peça orientação ao time; não crie outro owner para contornar o bloqueio.

Preparações anteriores sem seleção explícita de perfil permanecem preservadas e pedem revisão do time para retomar o mesmo owner. Não apague participant.json, não crie outro owner e não use seu perfil normal para contornar esse bloqueio.

Se uma sessão expirar mesmo com o login indicado como ativo, use **9 — Renovar login do perfil Code do piloto**. Ela abre novamente o fluxo oficial do mesmo perfil, com sua confirmação; o status de login sozinho não comprova uma chamada ao modelo nem a qualificação.

Depois de inscrita, a origem é recuperada pelo próprio instalador, inclusive se login ou qualificação de cliente ainda estiverem pendentes. Ela não é solicitada novamente e um caminho antigo guardado no kit não substitui o vínculo atual. Instalações anteriores conservam exatamente sua origem já inscrita; este fluxo não migra uma instalação que já apontava para a amostra local. Não edite `participant.json` ou o estado de instalação, não mova o brain e não crie outro owner para trocar a origem. Se o caminho inscrito precisar mudar, preserve a instalação e peça orientação ao time.

A escolha de cliente fica vinculada à instalação e não pode ser trocada editando arquivos. No Desktop somente, a opção de login do Code não é oferecida; a instalação normal da extensão e a importação da biblioteca de métodos continuam necessárias no Desktop. Agentes que executam pelo Code exigem sua preparação separada. Uma instalação anterior de Code e Desktop preserva sua escolha; este fluxo não a reduz automaticamente.
