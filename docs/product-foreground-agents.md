# Foreground Maestro agents through MCP

The admitted MCP now offers independent native draft/review execution in either
client through `agents.run`. Maestro coordinates the work and applies approved
filesystem effects through the existing canonical owners. Code's qualified host
Agent/Task path stays available. Desktop does not gain Code hooks.

## Prepare once

Open the participant management launcher and select `foreground-profile`.
Review creation of the owner-private foreground profile and complete its separate
official login. The manager reuses normal supported Code selection and native
observation. It preserves the daily Code profile, maintenance profile, owner brain
and shared source. No credentials or private profiles enter the distributed kit.

Preparation and login invoke no model and grant no background work. Each call
selects a provider label/model and receives a fresh exact owner review of up to
two native sessions under one deadline: synthetic local qualification, then the
independent role turn. The runtime
account determines routing; declared provider, actual response model/version and
observed provider usage metadata retain distinct meanings.

## Use from Code or Desktop

Ask Maestro to use an independent agent on explicitly selected material. The
operator method reads `agents.status`, announces an active canonical spoke,
and sends one bounded packet through `agents.run`. Status lists current scope,
actual availability and eligible roles without invoking a model or exporting
profile files. Account and Case remain session scopes; dormant agents stay dormant.

The owner sees task/context, role, exact current source/runtime/profile, complete
supported local instruction/settings/plugin closure and provider/model before
approval. The exact review also binds an explicit UNATTESTED remote/OS-policy
fact and startup/context exposure. Local startup context may be sent in both
sessions. Qualification stdin contains only a compiled fresh synthetic challenge;
private task/context/SELF are withheld until genuine supported-local probe
completion creates a one-use attempt-local capability. The actual role child is
independently re-observed before private stdin. The fixed runner re-enumerates
the original finite local closure before qualification, before private stdin,
during execution and before return, using the original native lifetime and
cancellation mechanics. It never borrows a weekly grant or imports serialized proof. The result is derived work, with actual runtime
session/model/version and available usage metadata. It grants no filesystem or
SELF authority. The server retains no foreground transcript, result or reusable qualification.
The two actual session IDs and their usage/cost metadata are reported separately;
known probe usage survives a later role failure without exposing role text.

A successful draft can be independently reviewed by a second permitted role.
Maestro saves only the approved synthesis through the existing page review,
then reads it back and captures selected continuity through the ordinary
memory/daily owners. The managed operator recipe carries the exact field contract.

## Qualification and limits

Local controlled fixtures validate schema/review/scope/output behavior. Native
acceptance must separately show two genuine calls in the final installed clients,
their independent runtime responses, approved save/readback and fresh-session
continuity. A role document, planner or execution ledger is not model execution.

Calls are finite: at most two sessions under ONE 60-second operation deadline,
128 probe plus 1920 role output tokens, 16 KiB selected serialized input,
32 KiB combined stdout and 4 KiB combined stderr. The actual role has one attempt/turn. Selected task/context have smaller independent limits.
The supported local worker requests no tools or direct filesystem effects.
Remote or OS-delivered policy remains UNATTESTED; observed local behavior does
not establish enterprise device-policy admission or production readiness. Scope/source/profile drift,
decline, cancellation and malformed output refuse a publishable result; prior
state remains unchanged. Closing a client cancels its active call rather than
creating unattended work. Windows native acceptance remains a separate gate.
