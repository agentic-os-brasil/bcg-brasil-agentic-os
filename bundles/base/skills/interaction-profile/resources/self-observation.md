# Reviewed professional self declarations

Use this branch only when the owner explicitly asks to remember, correct or withdraw a professional preference. Routine preflight, silence, generated work, observed patterns and repeated messages do not request self learning. Read the current public schemas and use only these owning operations; an unavailable operation stays pending without file or profile-application fallback.

1. Query `owner.observation.status`. Follow `next_offset` while `has_more` is true, at most 32 entries per page. Status contains intake/canonical IDs, states and revisions, never claim bodies. A missing or refused source does not authorize initialization or repair.
2. Propose one minimal declaration for the owner's exact review. `owner.observation.intake` accepts only nested `self_observation` fields: `signal` (explicit instruction, correction or endorsement), an admitted professional `facet`, `claim` (a short normalized code), declared `confidence` from 0 to 1 and `expires_at` within ninety days. Read the schema for exact values and limits. Never copy prompt, transcript, document or generated-output prose into a claim. Do not infer a psychological, personal or sensitive facet.
3. Let the trusted review display the complete declaration and its owner-global professional scope. Approval queues only proposal input; refusal, cancellation, unavailable review or expiry does not approve. Do not supply source digests, episode IDs, owner/declassification/confirmation flags, paths or a review digest. The server derives stable identity and binds the real trusted review. A declaration is owner-attested data, not native/conversation provenance. Fresh reviews and connections do not establish independent corroboration.
4. Re-query status after approval. `intake_state=approved` is pending intake, not canonical capture, active SELF or a changed communication profile. An identical declaration remains the same source after reconnect. Rejected/redacted declarations remain denied.
5. Only if the owner separately chooses automatic capture, inspect the current `maintenance.status` and exact review for `self-observation-capture`. Its qualification must commit a genuinely new canonical observation; enrollment is a separate choice. Intake acknowledgement or replay does not qualify it. A captured observation remains versioned proposal input, never active SELF.
6. To withdraw an existing declaration, call `owner.observation.reject` with the returned `intake_id` and `next` set to `rejected` or `redacted`, obtain its exact trusted review, then re-query status. Preserve concurrent or newer changes and report any refusal. Do not delete private files or use `owner.apply` to manufacture the outcome.

A professional preference becomes active only through its existing canonical owner-refinement policy and required review. This method grants no execution, provider, scheduling, tool or filesystem authority. Real host consent and qualification are distinct from operation discovery or a successful synthetic test.

If preserved observations require explicit setup after an upgrade, report that pending prerequisite. An operator closes older Maestro writers and repeats the existing local `maestro-mcp init` with the admitted binding; it validates the legacy log and admits its persistent selection lock without rewriting canonical observations. The method must not delete locks, recreate owner data, initialize through a query or bypass active/unsafe-state refusal. Resume status only after that explicit setup.
